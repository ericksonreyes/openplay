# ADR-0009: Documentation Visuals Are Generated Artifacts

## Status

Accepted

## Context

OpenPlay needs user guides and demo visuals for four frontends. Hand-captured screenshots rot the moment the UI changes, and retaking them manually is maintenance debt that never gets paid.

## Decision

All screenshots and recordings in documentation are produced by **Playwright capture scripts** run against the running Docker stack — never captured by hand.

- Capture scripts live in `scripts/screenshots/<channel>/<flow>.spec.ts`; generated output lives in `workspace/docs/screenshots/<channel>/`; per-channel guides live in `workspace/docs/guides/`.
- The channels are `public` (public site), `player`, `venue`, and `platform`.
- Scripts run against the running stack with seeded demo fixtures — real flows, real data, never production-like PII.
- Capture states, not just happy paths: empty state, validation error, loading, success.
- Player-facing flows are captured at a mobile viewport — the product is mobile-first.
- Video walkthroughs use Playwright `recordVideo` converted with `ffmpeg` for guide embedding.
- If a screenshot cannot be regenerated by a script, it does not belong in the guide.
- Conventions live in the `user-guide` agent skill.

## Reasons

- Generated visuals stay fresh: a screenshot that fails to regenerate is a broken build, not stale prose.
- The same Playwright dependency and running stack serve E2E tests ([ADR-0008](0008-e2e-testing-with-playwright.MD)) and documentation captures.
- Captures against a fresh E2E world produce deterministic doc data instead of accumulated dev artifacts.

## Consequences

- `workspace/docs/` becomes partially generated — contributors re-run capture scripts rather than pasting images.
- When a user-facing flow is added or changed, the capture spec, regenerated screenshots, and the channel guide update in the same change; every image path is link-checked like any other relative link.
- Playwright becomes a dev dependency once the first frontend lands.

## Alternatives considered

### Manual screenshots

Zero tooling, but they rot immediately. Rejected.

### Storybook or a component-shot service

Isolated component shots, but a second toolchain for coverage not needed at this stage. Revisit if component-level documentation becomes a need.

### Written docs without visuals

Cheapest, but the demo and onboarding value of visuals is the point. Rejected.
